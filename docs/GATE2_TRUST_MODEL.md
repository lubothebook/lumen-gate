# Lumen Gate 2.0 — Trust Model

Status: living document for the gate-2.0 line (HARDENING-2.0.md sections 4.7,
11, and the F8/F9 H-gate require it). Every claim below links to evidence in
`deployments/testnet-2.0.json` / `deployments/hardening-2.0.json` or says it is
pending. Nothing here is marketing copy; per the annex, where a comfort cannot
be provided, the discomfort is written instead.

## 1. What you are trusting, ranked

1. **Circle's attestation (root of trust).** Lumen Gate is not an issuer, not a
   reserve custodian, not a source-chain validator set. A claim is valid because
   Circle's Iris service attested a CCTP message; the on-chain
   `TokenMessageTransmitter` verifies that signature set. Circle can freeze
   USDC and can halt attestation. The UI must show "attestation pending"
   honestly and offer a re-query by transaction hash (annex 7).
2. **The destination CCTP contracts as deployed by Circle** — domain 27,
   `TokenMessageTransmitter` (`CBJ6MTCK…`), `MessageTransmitter`-pair and the
   Sepolia/Source `TokenMessengerV2` / `MessageTransmitterV2` addresses. These
   carry Circle-retained powers: pause, upgrade, deny-list, and
   `rescue_sep41` on the forwarder. That is Circle's surface, not ours; we
   record it, we do not inherit it.
3. **This repository's own deployed contracts** (the receiving `GateClaim` /
   spike gate, and once deployed, the `BurnRouter`). They are deliberately
   built with **no owner, no pause, no upgrade**. See §4 for what that implies
   when we are wrong.

## 2. What you are NOT asked to trust

- **No relayer, no operator key in the fund path.** A user's burn, Circle's
  attestation, and a permissionless `claim` call move funds. Whoever pays the
  fee may trigger a claim; nobody may block one. (Evidence: spike S2/S6 live
  reads; 1.0-lineage claim-plus-bound wording retained.)
- **No custody window.** The router never holds value across interactions: the
  conformance suite fuzzes that balance deltas are measured and conserved
  (gate2/evm, `testFuzz_RouterNeverGainsValue`, 500 runs; CI job `evm-tests`).
- **No admin mint.** Minting on the destination happens only via Circle's
  token contracts after a verified message; the receiving gate cannot mint at
  will. 1.0's `renounce_admin` proofs stay green (regression-gate job).
- **No unlimited approvals.** The user approves exact amounts; the router's
  own approval to the messenger is exact-amount with a zero resting
  allowance — asserted in `test_ApproveToMessenger_IsExactAmount_AndZeroAfter`.

## 3. The address-space risk we can and cannot remove

`hookData` embeds the recipient's Stellar strkey. A wrong strkey burns
irreversibly. Mitigations, in depth:

1. Contract-side full verification: Base32 charset, length 56, version char in
   {G, C, M}, and **CRC16-XModem checksum** — not a format proxy (annex 4.4).
2. Two separate negative tests (format vs checksum), plus a byte-byte golden
   hook generated by an independent Python oracle, not by the contract itself.
3. Frontend double-check: the UI verifies locally, then `eth_call`s
   `checkRecipient` on the deployed router and refuses on divergence (annex 7.1).
4. Residual, written down: if the CRC oracle and the contract agreed on a
   wrong-but-valid key (e.g., user pastes their friend's public key), the funds
   go where the bytes say. No contract can know intent. The UI shows the full
   strkey in a monospaced block before signing and repeats it in the receipt.

## 4. "What if a bug is found?" (annex 4.7 — the uncomfortable section)

- **The contracts cannot be fixed in place.** No upgrade, no pause, no admin.
  This is the deliberate trade of §2's benefits: the same absence that makes
  backdoors impossible makes patches impossible.
- The only kill switch is **removal from the frontend configuration**: the
  contract keeps existing on-chain, but the UI stops offering it, and no new
  burn can route through it. The `BurnRouter` holds no value between
  interactions, so a withdrawal-style emergency is structurally unnecessary —
  there is nothing to rescue. This claim is fuzz-tested, not asserted
  (23/23 suite green, including the dispatch-level adminless proof:
  `test_AdminlessSurface_DispatchLevelProof`).
- Funds already IN FLIGHT (burned on source, not yet claimed) are the danger
  window: the destination `GateClaim` stays callable permissionlessly, so a
  discovered receiver-side bug can freeze nobody's claim — but if the receiver
  itself were broken, claims would fail closed (error-coded refusals; see the
  spike gate's `Error::TransmitterRefused` design). Failure mode is "stuck,
  not stolen."
- Response protocol when a bug IS found: (a) open a post-mortem in the
  deployments manifest `findings[]` — entries are never deleted, only
  superseded with reasons; (b) deploy a NEW contract id, never touch the old;
  (c) move every frontend pointer, mark the old id in `superseded[]` with the
  reason; (d) re-run all `post_deploy_checks[]` plus the full conformance suite
  before the new id is offered. This is the pattern already exercised once:
  the assert-form gate was retired to `superseded[]` when the error-code policy
  landed, with the redeploy tx recorded.

## 5. Decimals, fees, and rounding (recorded so nobody re-derives it)

- CCTP moves USDC with a 6→7 decimal bridge across domains: source 6 decimals,
  Stellar USDC 7. The gate scales by ×10 with checked arithmetic (annex 5.3);
  the exact rounding direction and tier-boundary cases (9.999999 vs 10.000000,
  both directions) are pinned in `deployments/testnet-2.0.json` spikes and will
  be pinned in contract tests before F5 acceptance.
- Circle burns fees are explicit (`maxFee` pass-through; measured min-fee 0 for
  domain 27 on testnet, fee table fast 1 / standard 0). The UI must quote them,
  never absorb them silently.
- "attestation pending" is a UI state with a re-query affordance by tx hash;
  the claim button stays disabled until the message hash is verifiable via the
  documented public endpoint (two independent reads on the same nonce).

## 6. Key hygiene and roles (annex 9, already operational)

- Deployment key (`audit-probe`) has NEVER signed a user-facing transaction and
  only deploys; a separate runtime key performs test transactions. Least
  privilege by practice, recorded per deployment in the manifest.
- Secret scanning runs in CI on every push (gitleaks, fingerprint allowlist of
  15 triaged public identifiers — new values under old names re-alarm).
- `~/.git-credentials`-style local conveniences are excluded from snapshots by
  policy; nothing that can sign money lives in the workspace tree
  (`ls-files`-verified for `.spike-evm-key.json`, 0600, untracked).
