Lock

Value leaves the source chain into a lock event. The message id is derived from the source domain, the target domain, the block height, the event index, a nonce and the payload hash — never from anything the relayer chooses.

Prove finality, on-chain

A quorum of source validators signs the block. The registry verifies that aggregate BLS signature against its registered policy using Stellar's native BLS12-381 host functions, then stores the finalized state and event roots.

signature_set(3, 2) verified in-contract

Mint

A Merkle proof shows the single event belongs to that finalized root. The gateway checks the registry, checks the nonce high-water mark against replay, then mints and pays the relayer out of the transferred amount.

About

What the anchor is for, and what it is not

The anchor facade is an integration surface, not the trust anchor. It is the part other software talks to: discovery, a machine-readable manifest, the audit record, and an operator trigger. It holds no custody, no mint authority and no verification keys. If it disappeared, settlement would keep working — you would lose the window, not the rule.

Is this a zkVM?

There is a small machine here now, and it has a budget. One of the three Groth16 lanes proves the step-by-step execution of a committed program on a register machine with eleven opcodes, eight registers, sixteen memory words and twenty rows per proof: the program is a public input, every row decodes against it, memory is carried row to row, and the run is replayed by an interpreter in this repository before it becomes witness data. A proof of a sixteen-step run was accepted by a registry on testnet. It is not a general-purpose zkVM: a program that needs a twenty-first step has no proof in this circuit, there are no syscalls, and the guest is assembled from a listing rather than compiled. The other two lanes are statement proofs — a quorum of approval bits bound to three roots, and a chained state transition — and none of the three is a signature verifier, which is why settlement still anchors on the BLS lane, whose aggregate signature does cover the event root.

What does "gasless" mean here, exactly?

Zero spendable XLM on the receiving side. The relayer signs and pays the Stellar fee and is repaid in wrapped asset out of the transferred amount; the receipt shows a recipient whose XLM balance is byte-for-byte identical before and after, at exactly its minimum reserve. It does not mean zero setup: the recipient still needs an account and a trustline, because a Stellar asset cannot be held without one. Burning is not gasless.

Who can still change the rules?

Nobody. Both deployed contracts have renounced their admin capability on-chain, which freezes the verifying key, the BLS policy, the domain list, the target domain and the fee configuration. The audit loop proves it every round by simulating the admin action and requiring the host to trap. Before the renounce, the deployer could have changed all of it; that window is closed, and the receipts are in the manifest.

How do I reproduce any of this?

The repository has the deploy scripts, the circuit, the byte layout of the on-chain proof encoding, and the exact commands. Every receipt in the manifest was produced by those commands against testnet, and the documented limitations are the ones that are actually true today.
